# Nest Devtools comparison

Nest Devtools and nestjs-doctor both draw a NestJS module graph. They get it
from opposite ends.

Nest Devtools boots your application and introspects the injector graph Nest
built. nestjs-doctor reads the `@Module()` decorators in your source and never
runs anything. That difference decides which questions each one answers.

## How each one gets the graph

Nest Devtools takes a `DevtoolsModule` import plus a `snapshot` flag on
`NestFactory.create`. Your running app then exposes an extra HTTP server, on
port 8000 by default. The dashboard at devtools.nestjs.com reads the graph from
it in your browser. Nest's documentation says not to enable the module in
production.

nestjs-doctor takes a command:

```bash
npx nestjs-doctor@latest . --report
```

Nothing boots, nothing listens on a port, and the report is one HTML file on
disk. A scan reaches the same conclusion about a module that never starts
because a dependency is missing.

## Side by side

| | Nest Devtools | nestjs-doctor |
|---|---|---|
| Builds the graph by | Booting the app | Reading the source |
| Needs the app to run | Yes | No |
| Analysis | 11 fixed architecture checks | 52 rules across five categories |
| Rules configurable | No | Yes, plus your own |
| A finding points at | A graph node | A file and a line |
| Health score | None | 0 to 100 |
| Fails a build | No | Yes, by severity or score |
| Database schema | Not covered | ER diagram from four ORMs |
| License | Paid, 7 day trial | MIT |

The audit column is the one worth reading carefully. Nest Devtools does analyze
your graph, and its findings carry `error`, `warning` and `info` severities. The
checks are architecture heuristics with thresholds baked in, so there is nothing
to configure and nothing to add.

nestjs-doctor covers security, correctness, architecture, performance and schema,
and every rule can be disabled, re-weighted or written from scratch. See
[Rules](/docs/rules) and [Custom rules](/docs/rules/custom).

## In CI

Nest Devtools publishes serialized graphs to a central registry and shows a diff
between builds. That integration is on the Enterprise plan, and it reports
rather than gates.

nestjs-doctor runs anywhere Node runs and is built to fail a build. `--blocking`
gates on severity, `--min-score` gates on the score, and the GitHub Action
comments only on what a pull request introduced.
[Failing the build](/docs/ci/gates) covers the flags.

## What Nest Devtools does that nestjs-doctor does not

A static scan cannot see a running process, so several Devtools features have no
equivalent here:

- **The interactive sandbox:** executes code against your live application from
  the browser.
- **Dependency resolution debugging:** replays a "Cannot resolve dependency"
  error against the real injector.
- **Routes across transports:** WebSockets, gRPC and GraphQL resolvers, not only
  HTTP.
- **Graph diffs between builds:** shows which nodes a commit added, changed or
  removed.

If your question is why a specific instance behaves the way it does at runtime,
that is the tool for it.

## Using both

The two read the same underlying artifact, so they compose. `--timings` takes
the `SerializedGraph` Nest itself produces and overlays real construction times
on the module graph in the report. [Boot trace](/docs/report/boot-trace) covers
the change to `main.ts` that captures one.
