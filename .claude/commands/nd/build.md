You are running the `/nd:build` workflow on behalf of a developer.

Their input is: `$ARGUMENTS`

If `$ARGUMENTS` is empty, stop immediately and tell them to invoke this with an issue number, issue URL, or a one-line task description.

The workflow has two strict human gates:

1. **Spec gate.** After feature-dev finishes planning, it writes a markdown spec. The developer approves it before any code is written.
2. **Code gate.** After feature-dev finishes implementing, the developer reviews the local diff and approves before any branch is pushed.

The `/code-review:code-review` skill at the end is a public cross-check, not the developer's first or second look.

---

## Step 1: Resolve the task

- Matches `^#?\d+$` → GitHub issue number. `gh issue view <n> --json title,body,labels,state`.
- Contains `/issues/<n>` → extract the number, then same.
- Otherwise → free-form task description.

Restate the task in one short paragraph. If it's too vague to plan against, ask exactly **one** clarifying question and stop.

## Step 2: Pre-flight checks

1. Current branch is not `main`. If it is, `git checkout main && git pull`.
2. `git status --porcelain` is clean outside `.claude/specs/`. Refuse on a dirty tree.
3. `.git/shallow` does not exist.
4. `gh auth status` reports authenticated.

Any failure stops the run. Do not proceed silently.

## Step 3: Create a working branch

Slug: the issue number (`issue-109`) or the first 3–5 dash-separated words of the description, alphanumeric and dashes, capped at 40 chars.

Branch: `feat/<slug>` — `fix/` when it's clearly a bugfix. Add a `-YYYYMMDD-HHMMSS` UTC stamp only if that branch already exists.

`git checkout -b <branch>`.

## Step 4: Run feature-dev — the spec gate happens inside Phase 4

Invoke the `feature-dev:feature-dev` skill via the `Skill` tool with the resolved task plus this preamble:

> **Auto-mode addendum (inside `/nd:build`):**
>
> The branch is already created (`<branch>`); commit there, do not switch branches.
>
> - **Phase 1 (Discovery)** — proceed.
> - **Phase 2 (Codebase Exploration)** — dispatch code-explorer agents as usual.
>     - **First, check whether an `nd-*` domain agent owns what you're touching** (`ls .claude/agents/`). If one does, consult it via the `Agent` tool *before* the generic explorers — it already holds the subsystem's invariants and footguns.
>     - The generic explorers still run for whatever neither covers.
>     - Read `CLAUDE.md` → "Things that bite in this repo" before designing anything that touches paths, git, or platform behaviour. Every entry there is a bug that already shipped.
> - **Phase 3 (Clarifying Questions)** — SKIP the approval gate. Make reasonable assumptions and record them under "Assumptions" and "Open questions".
> - **Phase 4 (Architecture Design)** — dispatch code-architect agents as usual. After picking the pragmatic-balance approach, **before presenting options**:
>     1. `mkdir -p` the parent of `.claude/specs/<branch>.md` (the branch contains a `/`).
>     2. Write the spec using the template below. This is a LOCAL PLANNING ARTIFACT — never `git add`ed, never in a commit, never in the PR.
>     3. Present it with the approve/change/question/regenerate/cancel prompt. Wait for explicit approval, looping on changes. On approval set `**Status:** approved` and go to Phase 5. On cancel, stop.
> - **Phase 5 (Implementation)** — SKIP the start-of-phase gate. The approved spec is the plan.
> - **Phase 6 (Quality Review)** — HONOR the gate. Dispatch the `feature-dev:code-reviewer` agents on the local diff, present findings with "fix now / fix later / proceed as-is".
> - **Phase 7 (Summary)** — proceed.
>

## Step 5: Verify the working tree

1. `git status --porcelain` — the spec file must be untracked. If it got staged, `git restore --staged .claude/specs/<branch>.md`.
2. `git log --oneline main..HEAD` — if empty, feature-dev produced nothing. Report and stop.
3. Commit anything left unstaged under a conventional message. **No `Co-Authored-By` or `Claude-Session` trailer.** Husky runs automatically; never `--no-verify`.
4. Capture `git diff --stat main..HEAD` and the log for the next step.
5. Cross-check the spec's "Files expected to change" against `git diff --name-only main..HEAD`. Flag divergence in Step 6.

## Step 6: Code checkpoint — STOP and ASK

Nothing is pushed yet. Present:

```
### Code ready for your review

**Task:** <restated>
**Branch (local):** <branch>
**Spec (local, approved):** .claude/specs/<branch>.md
**Diff:** <git diff --stat>
**Commits:** <git log --oneline main..HEAD>

**feature-dev Phase 6 findings:** <summary + what was done>
**Spec vs implementation:** <"matches" or "diverged — expected A, got B">

**What you can do:**
- 'ship it' / 'yes' → I push and open the PR
- 'fix: <what>' → I iterate on the branch
- 'show diff' → I print the full diff
- 'cancel' → branch stays local, I stop
```

Then STOP. Only an unambiguous approval pushes.

## Step 7: Push + open PR (only on approval)

```bash
git push -u origin <branch>
gh pr create --title "<conventional commit title>" --body "<PR body>"
```

Not a draft.

### PR body — six sections, in this order

```markdown
## 1. Context

<What the reader must know before the problem makes sense. The system fact, not
the bug. 2-4 sentences.>

## 2. Problem

<What is broken and the evidence it is broken. Lead with the sharpest fact.
Prefer a number, a table, or real output over a paragraph.>

## 3. Possible flows

<Every path into the thing you changed, and which were affected. Almost always a
table. This is where you prove you didn't fix only the obvious one.>

## 4. Solution

<What you did, in a few words. Name the mechanism. Say what you did NOT do, and
why.>

## 5. Before vs after

<A table. One row per behaviour that changes. Include an unchanged row so the
reader sees the blast radius is bounded.>

## 6. Example

<One real invocation. The old output. The new output. Copy-pasteable.>

<if an issue was resolved>
Closes #<n>.
</if>
```

### How to write it

- **Short sections.** A few lines each. If a section needs a paragraph, you haven't found the point yet.
- **Plain words.** No "leverage", "robust", "comprehensive", "ensure", "seamless". Write it as you'd say it out loud.
- **Evidence, not adjectives.** "9 tests failing across relative imports, aliases, and barrels" beats "significant resolution issues". Show the number, the table, the output.
- **No overexplaining.** State a fact once. Don't restate it in the next section.
- **Section 3 is the one people skip — don't.** It shows you checked every entry point (CLI flag, API call, scope mode, platform), not just the one in the issue.
- **Section 5 must include an unchanged row.** A reviewer's first question is "what else does this break?" — answer it before they ask.
- **Section 6 must be real.** An actual command you ran, with actual old and new output. Not a sketch.

Drop a section only if it is genuinely empty. Never pad one to fill space.

No "Test plan" / "Notes" / "Process" sections. Never reference or paste the spec file — it is local-only.

Capture the PR number and URL.

## Step 8: Simplify + code-review convergence loop

Run the public cross-checks as a **loop, not a one-shot** — any commit pushed to the PR resets the review state, so a review of an older head proves nothing about the current one:

1. Invoke the `simplify` skill on the branch diff vs base. If it applies fixes, run the affected tests, commit, push.
2. Invoke `code-review:code-review` with the PR number against the **current** head. Commit and push any fixes made on the branch.
3. **Converged?** Step 1 applied nothing AND step 2 produced no fix commits and no ≥80 findings → done.
4. Otherwise a new head exists that no pass has cleared — go back to 1.

Cap at 3 iterations. If still not converged, stop looping and surface what remains in Step 9.

## Step 9: Surface final state

```
### /nd:build complete

**Task:** <one sentence>
**Branch:** <branch>
**Spec (local, not in PR):** .claude/specs/<branch>.md
**PR:** <url>
**Local review (Phase 6):** <summary>
**Public code-review:** <"No issues found" or "N issues, see <url>">

**Below-threshold FYI:**
- <findings, if any>

**Suggested next step:**
- "Request reviewers and merge when approved"
- "Address the N findings before merging"
- "Blocker: <reason> — discuss before merging"
```

Then stop. Do NOT auto-merge. Do NOT delete the spec file.

## Guard rails

- **No implementation without spec approval** at the Phase 4 gate. Headline invariant #1.
- **No push without code approval** at Step 6. Headline invariant #2.
- **A review only counts against the head it ran on.** Any commit pushed after a simplify/code-review pass re-enters the Step 8 loop. Never report "complete" with commits no pass has cleared.
- The spec is never `git add`ed and never appears in the PR. Always use explicit paths in `git add`; never `git add .` or `-A`.
- Never commit directly to `main`.
- Never `git push --force`, `--no-verify`, or any hook-bypass flag.
- Never `gh pr merge` or `gh pr ready`. The human marks ready and merges.
- **No `Co-Authored-By` / `Claude-Session` commit trailers.** Bot attribution in the PR description is fine.
- If CI adds a platform job (macOS, Windows, an older Node), expect it to find pre-existing bugs. Report them; don't silently widen scope to fix them without saying so.

## What this command is NOT

- Not a ship-to-prod button — it stops at an open PR with reviewers not yet requested.
- Not a refactor tool — large refactors deserve their own design step.
- Not a documentation generator — the spec is for the developer's eyes, not a substitute for the PR description.
